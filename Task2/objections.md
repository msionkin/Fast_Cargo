# Отработка возражений по плану трансформации Fast Cargo

## 1. Техлид Fast Cargo

> «Временное решение для DWH создаст риски для стабильности текущих отгрузок и потребует переписывания легаси-кода».

**Ответ.** Контур DWH только читает журнал изменений СУБД и не вмешивается в работу монолита. Код не меняется ни в переходный период, ни позже: на горизонте года легаси выводится из эксплуатации, а не переписывается.

- **Код монолита не меняется.** Debezium читает WAL, который PostgreSQL пишет и так. Меняется только конфигурация СУБД (`wal_level = logical`, слот репликации): один перезапуск в ночное окно после прогона на стенде.
- **Нет SQL-нагрузки.** CDC не выполняет SELECT по рабочим таблицам. Историю загружаем из бэкапа, восстановленного на отдельном инстансе.
- **Сбой CDC не останавливает отгрузки.** Коннектор останавливается, монолит работает как раньше, откат занимает не больше 15 минут.
- **Контроль у техлида.** Техлид — совладелец пакета работ CDC → DWH с правом остановить ввод. Перед вводом две недели теневого режима со сверкой данных.

**Фиксируем:** ADR «Log-based CDC для DWH», критерии приёмки и план отката из раздела 7 плана трансформации.

## 2. Отдел информационной безопасности «Плюс Ритейл»

> «Интеграция CRM нарушает требования 152-ФЗ, так как персональные данные лежат в общем контуре монолита».

**Ответ.** CRM не подключается к монолиту и его БД. Она получает только данные с токенами вместо ПДн, а сами ПДн с месяцев 4–6 хранятся в отдельном изолированном сервисе.

- **Нет прямого доступа.** Сетевые политики запрещают внешним системам доступ к транзакционной БД. CRM получает данные только через API Customer 360 в APISIX (mTLS, OAuth 2.0).
- **Переходный период.** Паспорт, телефон и email маскируются в коннекторе Debezium до записи в Kafka, поэтому ПДн не покидают контур монолита. CRM подключается только после запуска сервиса профилей.
- **Целевое состояние:**
  - сервис профилей — единственное хранилище ПДн, со своей БД в отдельном сегменте сети, данные на диске шифруются;
  - остальные сервисы, Customer 360 и шина работают с токенами (UUID).
- **Минимизация доступа.** Оператор CRM получает ПДн конкретного клиента по запросу к сервису профилей. Доступ проверяется по роли, каждое обращение журналируется.
- **Аналитика.** В DWH уходят только обезличенные данные.
- **Каналы.** Канал между ЦОД Fast Cargo и холдинга защищён сертифицированными ГОСТ-VPN-шлюзами холдинга, внутри контура используется TLS/mTLS.
- **Согласование до запуска.** До подключения CRM ИБ холдинга согласует модель угроз и уровень защищённости ПДн.

**Фиксируем:** ADR «Изоляция ПДн в сервисе профилей и токенизация», схема сетевых доступов, модель угроз.

## 3. Производственный департамент «Плюс Ритейл»

> «Поток телематики IoT на 3000 RPS создаст цунами данных и мгновенно уронит текущую инфраструктуру и СУБД».

**Ответ.** Телематика не попадает ни в текущую инфраструктуру, ни в СУБД монолита. Её принимает отдельный горизонтально масштабируемый контур, а Kafka сглаживает пики.

- **Изолированный контур.** MQTT-брокер (VerneMQ) → Kafka → ClickHouse. Монолит и PostgreSQL в этом потоке не участвуют.
- **Объём в цифрах:**
  - 3000 сообщений/с × ~300 байт ≈ 1 МБ/с, то есть не больше ~80 ГБ сырых данных в сутки даже при круглосуточном пике;
  - после сжатия в ClickHouse ≈ 8 ГБ в сутки;
  - для кластера Kafka из 3 брокеров это меньше 10% пропускной способности.
- **Без потерь при сбоях:**
  - трекеры отправляют данные по MQTT с QoS 1 и буферизуют их при обрыве связи;
  - Kafka хранит поток 72 часа: если ClickHouse или потребители деградируют, данные накапливаются и затем довычитываются.
- **Нагрузка на хранилище минимальна.** ClickHouse пишет пакетами раз в 1–5 с, это единицы вставок в секунду вместо 3000. В сервис «Доставка» передаётся только последняя координата каждой машины, не чаще раза в 30 с, поэтому транзакционная БД доставки не получает поток 3000 RPS.
- **Изоляция ресурсов:**
  - отдельные топики и квоты Kafka для IoT, поэтому заказы и EDI не конкурируют с телематикой;
  - отдельный пул узлов Kubernetes с лимитами ресурсов.
- **Подтверждение до запуска.** Нагрузочный тест на 6000 RPS (двукратный пик) проводится до подключения датчиков. Сайзинг считается в первый месяц, пики сверх резервов ЦОД покрываются облаком РФ с оплатой по потреблению.

**Фиксируем:** ADR «Контур IoT-ingest: MQTT + Kafka + ClickHouse», NFR: 3000 RPS, 0 потерь, буфер 72 часа.
